## 1. 修 `GOAL_WORK_ORDER_ACTIVE_SCOPE_CHANGED`（D 的下一步 1）

**D 猜的两条路线（(a) 改次序 / (b) 改 `deriveGoalWorkOrderIntentId`）都不是成因。** 实测调用栈：

```
V2DurabilityCoordinator.saveProjectState (durability.ts:2842)
  ← Object.save (gate1.ts:1402)
  ← admitProject (project-admission.ts:2023)      // 首次立项那条（无 goalWorkOrderId）
  ← authoritativeContext (main-adapters.ts:905)
```

失败的身份是 **`intent:gate1-starter:<world>:baseline:save:2b42bd9a…:branch:62e4e251…`**，不是任何 goal-work-order 身份。所以 (a)/(b) 都不解决它。

**真实账本形状**（磁盘 `execution-branches/62e4e251…/ai-mayor-v2.json`）：`projectState = PLACEHOLDER` + `activeGoalWorkOrderId` 指向 163 条旧 work order 之一（其 `updatedAt ≤ 18:42Z`，早于 19:13Z 的 re-baseline）。于是每个 tick 都走「首次立项」，然后被那条陈旧 work order 以 scope 不符拒绝，`journalPosition` 冻在 222 —— 连 6 次同一错误。

**成因**：re-baseline 只在一个点做了「计划随 authority 一起退休」；而 `activate()` 里**另一个丢掉 projectState 的点**（`!keepsProjectState`，durability.ts 约 4042）只丢 projectState、把整套 plan 留在账上。二者共存即死锁。

**修法（唯一一处新代码）**：`#retirePlanWithoutProject()` —— **PLACEHOLDER 的 projectState 与任何非空 plan 不能共存**；一旦同时出现，就把 plan 退休（`activeGoalWorkOrderId = null` + `goalWorkOrders = []`）。它挂在 `activate()` 里，因此覆盖**所有**会丢弃 projectState 的站点（含回滚边界恢复），而不是再补一个点。
